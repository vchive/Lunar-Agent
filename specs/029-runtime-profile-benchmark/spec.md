# Feature Specification: Runtime Profile Benchmark

**Feature Branch**: `029-runtime-profile-benchmark`
**Created**: 2026-09-03
**Status**: Implemented
**Input**: Benchmark repository-owned runtime profiles without importing an external harness

## Context and scope

Features 027–028 compare search strategies, but the model invocation profile is still supplied only
by library factories. A local algorithm researcher needs to measure the same strategy with a
one-shot runtime and with the bounded tool-capable `AgentLoopRuntime`. This feature exposes those
explicit runtime profiles through `benchmark`, while retaining the existing strict candidate and
evaluation bridges.

The benchmark runs one profile per invocation. Reusing the same contract, commands, seed, and
budget across two report directories gives an apples-to-apples one-shot versus loop comparison.
The runtime is created afresh for every strategy and role, and no Hermes/OpenCode/Codex/Harness
installation is discovered.

## User stories and acceptance scenarios

### User Story 1 — Benchmark an explicit runtime profile (P1)

1. Given `--agent-runtime openai-compatible` and an endpoint/model, when `benchmark` runs native
   strategies, then unconfigured solver/evaluator roles use repository-owned runtime adapters.
2. Given `--agent-runtime-loop`, each role uses bounded local tools and keeps the same strict
   CandidateDraft/EvaluationReport contracts.

### User Story 2 — Compare one-shot and loop fairly (P1)

1. Loop settings (max steps, exec, memory, transcript) are included in runtime fingerprints and
   report config.
2. Running the same contract and budget in separate workspaces produces comparable per-strategy
   metrics without shared runtime state.

### User Story 3 — Keep provider boundaries explicit (P1)

1. Missing endpoint, invalid profile combinations, disabled exec, malformed tool calls, and invalid
   evaluator JSON fail closed within the affected strategy/report.
2. API keys are accepted through the explicit flag/environment handoff and never appear in report,
   state, argv, or prompts generated by Lunar-Agent.

## Functional requirements

- **FR-2901**: Allow `benchmark` native strategies to fill solver/evaluator roles with `mock`,
  `subprocess`, or `openai-compatible` repository runtimes.
- **FR-2902**: Expose the existing bounded loop flags for OpenAI-compatible profiles.
- **FR-2903**: Construct a fresh runtime/tool registry per strategy role and preserve workspace
  confinement, optional memory, no-shell exec, and transcript bounds.
- **FR-2904**: Include credential-safe runtime fingerprints, including loop settings, in the report
  configuration.
- **FR-2905**: Reject runtime plus OpenEvolve in one benchmark invocation; OpenEvolve remains an
  explicit external strategy and can be compared in a separate run.
- **FR-2906**: Preserve Feature 027/028 command-backed behavior and default strategy selection.

## Success criteria

- **SC-2901**: A fake OpenAI-compatible endpoint can run a benchmark using both native strategies
  with `--agent-runtime-loop` and return valid candidates/reports.
- **SC-2902**: The same fixture works in one-shot mode and loop mode, with distinct fingerprints.
- **SC-2903**: Invalid runtime option combinations are rejected before strategy execution; API keys
  do not occur in persisted JSON.
- **SC-2904**: Full legacy and benchmark tests remain green.

## Out of scope

- Automatic provider discovery, remote queues, parallel model sessions, or a hosted service.
- A single invocation that mixes OpenEvolve with runtime profiles.
- Statistical ranking or quality claims beyond the emitted evidence.
